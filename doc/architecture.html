Module d'automation Sekoia

Slack Audit Logs

Ce module collecte les événements d'audit d'une organisation Slack Enterprise Grid et les pousse dans un intake Sekoia. Il tient en six fichiers et 260 instructions — dont la quasi-totalité existe pour une seule raison : l'API Slack renvoie les événements du plus récent au plus ancien et refuse de trier autrement. Ce document explique pourquoi cela coûte si cher, et comment le code s'y prend.

SDK sekoia-automation 1.24.0· Python 3.11· uv· 82 tests · 98 % de couverture
1 — Le problème

Pourquoi ce n'est pas dix lignes

Slack tient un journal d'audit de l'organisation : connexions, téléchargements de fichiers, installations d'apps, changements de rôles, anomalies. Ce journal ne sort que par GET /audit/v1/logs, avec pagination par curseur.

La version naïve avance son repère temporel page par page. Elle perd des données silencieusement : comme la première page est la plus récente, le repère saute presque jusqu'à maintenant dès le premier appel, et tout ce que le cycle n'atteint pas ensuite se retrouve derrière — donc jamais relu. Ça arrive à la moindre troncature de pagination, au premier 5xx, à chaque redémarrage de conteneur (le SDK en force un après six heures d'inactivité), et à chaque redéploiement.

Le contrat visé est celui d'un SIEM : un trou est le pire résultat, un doublon le deuxième pire. Tenir les deux demande deux morceaux d'état persistant et une façon de balayer le temps qui ne dépend jamais de l'ordre dans lequel Slack répond.

2 — Vue d'ensemble

Où tourne quoi

Le module ne s'exécute pas chez nous : Sekoia clone le dépôt, construit l'image et lance le conteneur sur sa propre infrastructure. Le connecteur tire depuis Slack et pousse vers un intake, identifié par une clé. Le parsing en ECS est le travail d'un artefact séparé, le format d'intake, qui vit dans un autre dépôt.

Pourquoi le module occupe la racine du dépôt. L'import Sekoia prend une URL de dépôt et rien d'autre : pas de sélecteur de sous-répertoire. Le module ne peut donc pas être un sous-dossier d'un dépôt plus large. Un dépôt par API, nommé sekoia-integration-<vendor>-<api>.
3 — Le mécanisme

Balayer le temps vers l'avant, valider vers l'arrière

La collecte avance par fenêtres d'une heure bornées par oldest et latest. Le repère ne franchit une fenêtre qu'une fois celle-ci entièrement drainée et poussée. Tout le reste — curseur persisté, bornes gelées, registre d'identifiants — sert à rendre une interruption inoffensive.

ÉtatFichierRôle
Repère (watermark)context.json, géré par le CheckpointTimestamp du SDKFin de la dernière fenêtre pleinement drainée. N'avance jamais au-dessus d'événements non poussés.
Fenêtre en volpending.jsonwindow_start, window_end (gelée), cursor, pushed_ids, truncated. Permet à une fenêtre interrompue de reprendre exactement, et supprime les re-push lors d'une relecture.

Deux fichiers, pas un. PersistentJSON.load() ne relit que si son dictionnaire est vide, et dump() réécrit le fichier entier : deux instances sur context.json s'écraseraient mutuellement.

Trois implémentations indépendantes convergent sur cette forme — le connecteur codeless de Microsoft Sentinel déclare les mêmes fenêtres oldest/latest et la même pagination sur next_cursor ; la TA officielle de Splunk la code. La différence est l'état : Sentinel n'en garde aucun (un redémarrage en milieu de fenêtre relit ou saute), et Splunk représente un curseur en échec inchangé à chaque exécution — donc un curseur que Slack cesse de reconnaître bloque cette entrée définitivement. La relecture unique depuis le début de la fenêtre, ici, existe pour ça.
4 — Le code

Fichier par fichier

Le module n'implémente que iterate() et frequency. Le SDK ≥ 1.23 possède déjà run(), le découpage en chunks, le push vers l'intake, la pause de fréquence et les métriques. Pas de while self.running, pas de metrics.py.

slack_audit_logs_modules/models.pyconfiguration du module — 15 lignes

Deux champs pydantic v2 : token et base_url. Le token porte json_schema_extra={"secret": True} — c'est ce que le générateur traduit en "secrets": ["token"] dans manifest.json, donc ce qui fait que la console masque et chiffre le champ.

pydantic v2 est non négociable : le générateur appelle model_json_schema() et lit FieldInfo.json_schema_extra. Un modèle pydantic.v1 le casse silencieusement.

slack_audit_logs_modules/errors.pyhiérarchie d'erreurs — 10 lignes

Trois classes. SlackAuditLogsError couvre tout échec de dialogue avec l'API ; AuthenticationError et PlanError en dérivent.

Séparer les deux dernières n'est pas cosmétique : c'est la différence entre « il faut un nouveau token » et « le token va bien, c'est le plan Slack qui n'expose pas l'API ». Ces deux cas sont aussi les seuls exclus du rattrapage sur curseur périmé — un token révoqué ne doit jamais être signalé comme un curseur invalide.

slack_audit_logs_modules/client.pyHTTP, pagination, mapping d'erreurs — 100 lignes

Le client est une requests.Session qui monte un LimiterAdapter(per_minute=…, max_retries=Retry(total=5, backoff_factor=1)). Limitation de débit, réessais et respect de Retry-After sont donc du comportement de bibliothèque, pas du nôtre — c'est la forme utilisée par les modules Tehtris et SkyhighSecurity de SEKOIA-IO/automation-library.

iter_pages()Génère (entrées, curseur_suivant) pour chaque page de la fenêtre. Curseur vide = fenêtre drainée. Curseur non vide sur la dernière page rendue = budget de pages épuisé, à repasser tel quel au cycle suivant.
MAX_PAGES = 100Garde-fou : un backlog ne peut pas faire tourner un cycle indéfiniment.
page vide → yieldVolontaire : le curseur est un progrès que l'appelant doit enregistrer, même quand la page ne contient aucun événement.
AUTHENTICATION_ERRORS7 codes Slack — not_authed, invalid_auth, invalid_authentication, token_revoked, token_expired, missing_scope, not_allowed_token_type.
PLAN_ERRORSpaid_only, feature_not_enabled, org_login_required.
_error_code()Slack répond parfois 200 OK avec {"ok": false, "error": …} : le code d'erreur est donc lu dans le corps, avec repli sur le statut HTTP si le corps n'est pas du JSON.

Aucun encodage manuel du curseur n'est nécessaire : le passer par params= de requests encode le = final en %3D automatiquement. Le connecteur de Sentinel, lui, doit ajouter un hook dédié pour ça.

Une alternative testée puis rejetée : un wrapper autour de LimiterSession. Son limit_statuses=(429,) remplit le seau dès le premier 429, ce qui bloque la requête suivante jusqu'à une minute en ignorant Retry-After — un second backoff empilé sur celui qu'on venait d'écrire.

slack_audit_logs_modules/connector.pyle cœur — 415 lignes

Tout ce qui suit sert la même propriété : ne jamais avancer le repère au-delà de ce qui a réellement atteint l'intake.

iterate() · L202Boucle sur les fenêtres tant que oldest ≤ now − timebuffer. oldest = checkpoint.offset + 1 : le oldest de Slack étant inclusif, ce +1 est ce qui empêche une double livraison à la frontière.
WindowProgress · L36Dataclass de l'état en vol. drained n'est jamais persisté — il décrit le cycle courant, pas la fenêtre.
_resume() · L157Rend l'état stocké seulement si window_start correspond ; sinon une ardoise vierge. La clé vient du repère validé, donc elle survit à un redémarrage.
_drain() · L274Lit une fenêtre. Si Slack rejette le curseur stocké, l'efface d'abord (pour qu'un second échec ne le repropose pas), prévient, puis relit la fenêtre depuis son début — le registre d'ids retient ce qui a déjà été envoyé.
_read() · L308Ordre critique (L329-339) : yield d'abord, puis extension du registre, puis _remember(). Ni le curseur ni le registre ne sont jamais écrits en avance sur ce qui a été poussé.
push_events_to_intakes() · L129Surcharge : si un chunk n'a pas atterri, lève. La fenêtre reste non validée et sera relue au cycle suivant depuis le curseur de pending.json.
_send_chunk() · L113Compte l'échec dans un finally — voir l'encadré ci-dessous.
_trim() · L190Borne le registre à LEDGER_PAGES × limit ids. Non borné, il atteindrait MAX_PAGES × limit ids réécrits en entier après chaque page — des mégaoctets d'écriture par cycle.
_report_oversized() · L345Un événement dont le JSON dépasse la limite par événement de la plateforme est jeté par le SDK avant qu'un chunk existe : rien à réessayer, et bloquer la fenêtre la figerait pour toujours. Le connecteur nomme donc l'id et la taille en critical. Le SDK, lui, n'en logue qu'un décompte en info.
_identifier() · L384Une entrée sans id n'est jamais retenue : rien ne distingue une re-livraison d'une seconde entrée réellement distincte, et le contrat place le doublon au-dessus de la perte.
gestion OSError · L259Enveloppe tout iterate(). Dans l'image, data_path retombe sur /symphony_data que rien ne crée ; chaque accès à l'état écrit (PersistentJSON écrit même en simple lecture), donc l'échec peut survenir au repère, à _resume, ou à _remember après le push. Seul un handler externe attrape tous les ordres.
next_run() · L102Rallonge le cycle jusqu'à frequency. Le SDK saute sa propre pause dès qu'un cycle a poussé un événement : sans ça, une organisation active serait interrogée à plein régime sur un quota partagé.
horloge en arrière · L214Si une fenêtre gelée finit après la frontière, le cycle s'arrête en avertissant plutôt que de valider au-delà du tampon.
Pourquoi le finally dans _send_chunk. Le gestionnaire d'échec du SDK appelle self.log(), qui est un POST synchrone vers l'API Sekoia. Quand la plateforme est injoignable — c'est-à-dire précisément la panne qui vient de casser le push vers l'intake — ce log relève, et l'exception est avalée par le wait_futures du SDK. Compter sur un retour normal de super() raterait donc entièrement le cas. Le compteur est incrémenté quand la clé du chunk est absente de collect_ids, ce que le SDK n'insère qu'après un POST réussi : son absence signifie exactement « ce chunk n'a pas atteint l'intake ».
slack_audit_logs_modules/validator.pytest d'identifiants — 48 lignes

Un appel authentifié bon marché (limit=1 sur une fenêtre de 5 minutes) et trois verdicts distincts : token rejeté, plan insuffisant, ou API en panne mais token probablement bon. La console offre ainsi un bouton « tester les identifiants » qui rend la vraie cause.

Le client est construit à l'intérieur du try, et un except Exception final ferme la marche. Module.run() du SDK n'enveloppe execute() que dans un try/finally, sans except : toute exception échappée sauterait send_results() et laisserait la console sans verdict du tout — un échec pire qu'un échec, parce qu'il ne dit rien.

C'est l'incident le plus probable de cette intégration : le token est émis par un humain et peut être tourné par l'administrateur Slack à tout moment.

5 — Réglages

Ce qu'un opérateur peut changer

Toutes les valeurs sont bornées côté modèle, et ces bornes se retrouvent dans le JSON du connecteur : une faute de frappe en console est refusée au lieu de devenir un incident silencieux.

RéglageDéfautBornesEffet
token—secret, requisToken utilisateur Slack (xoxp-…) portant auditlogs:read.
base_urlhttps://api.slack.com/audit/v1—Utile surtout pour pointer un double de test.
intake_key—requisL'intake Sekoia qui reçoit les événements.
frequency60 s10 – 3600Durée minimale d'un cycle, imposée même quand le SDK voudrait enchaîner.
limit10001 – 9999Événements par page. Le bon levier pour rattraper un retard — préférable à monter le débit.
ratelimit_per_minute301 – 50Le quota Slack (Tier 3, ~50/min) est compté au niveau de l'organisation, partagé avec toutes les autres apps du client. À monter en dernier recours.
timebuffer60 s1 – 3600Grâce laissée à l'indexation Slack. La borne basse à 1 est délibérée : 0 validerait latest = now et enterrerait définitivement tout ce que Slack indexe après.
lookback_seconds3600≥ 60Profondeur du premier démarrage. Ne s'applique que si aucun état n'existe.
6 — Limites

Ce qui peut encore se perdre, et comment on l'apprend

Le module est construit pour qu'une perte soit soit impossible, soit annoncée. Quatre chemins restent.

CheminPourquoi c'est irréductibleLe signal
Un événement dont le JSON dépasse la limite par événement de la plateformeLe SDK le jette avant qu'un chunk HTTP existe : rien à réessayercritical nommant l'id et la taille — la trace exacte de ce qui n'est jamais arrivé
Un événement exposé par Slack au-delà du tampon, daté avant le repèreLa latence d'indexation de Slack n'est pas observable depuis l'APIAucun, par construction. D'où la vérification de timebuffer sur les premières semaines de production
La rétention Slack qui expire pendant une panne très longueLes événements n'existent plus côté SlackIndirect : la métrique events lag du SDK. L'âge du repère n'est exposé nulle part
Un crash tronquant context.jsonLe SDK écrit sans temp-and-rename ; un fichier partiel se décode en {} et remet le repère à now − lookback_secondsAucun. Après tout crash dur de l'hôte, lire context.json avant de relancer

Tout le reste coûte des doublons, jamais une perte : un chunk échoué abandonne toute la page et la relivre au cycle suivant, un curseur rejeté relit sa fenêtre, et un registre tronqué peut repousser quelques événements lors de cette relecture. Le connecteur avertit dans les trois cas.

7 — Développer

Les commandes qui comptent

# installer et lancer la suite
uv sync
uv run pytest

# régénérer manifest.json, connector_*.json et main.py depuis les modèles
uv run sekoia-automation generate-files-from-code
# puis vérifier que register_account_validator est toujours dans main.py

# construire l'image comme le fait Sekoia
docker build -t slack-audit-logs .

Le module est un projet uv (uv add, uv sync, uv.lock versionné) parce que c'est ce qu'attendent le scaffolder et son Dockerfile. La documentation Sekoia décrit encore un flux poetry et des manifests écrits à la main : quand la documentation et le SDK divergent, c'est le SDK qui tourne.

Documentation d'architecture du module. Le suivi de déploiement, la procédure d'obtention du token et le runbook d'exploitation sont tenus hors de ce dépôt.
